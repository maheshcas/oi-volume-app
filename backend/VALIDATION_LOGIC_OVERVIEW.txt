OptionLens Validation Logic Overview

Maintenance rule
- Update this file whenever backend or frontend logic changes affect signal computation, state persistence, field mapping, UI interpretation, or validation behavior.

Current Backend Validation Priorities

1. Trap stack
- Range sessions should no longer show structurally inflated trap all day.
- Validation sequence:
  - Gate 1: median trap on quiet Range Day should generally sit below 62.
  - Gate 2: readiness should be able to rise above 57 when trap falls below 60 and no other blocker wins.
  - Gate 3: if readiness_active is true and trap < 60 but action remains WAIT, the remaining blocker is the LONG BIAS promotion guard in background_updater.py.

2. Breach stack
- Large moves must confirm through either current-level breach logic or previous-level override logic.
- Violent moves should not depend on fresh OI confirmation when distance fallback already proves abandonment.

3. SR stability
- Immediate support/resistance should not ping-pong on small OI rank noise.
- Candidate regime accumulation depends on stable SR levels.

Trap Engine
backend/app/engines/trap_engine.py
- Trap is built in layers:
  - structural validity failure
  - rejection wick score
  - hold-time failure
  - continuation failure
  - volatility factor
  - absorption score
- Core normalized validity score:
  - 0.40 * breakout_strength
  - 0.25 * atm_participation_score
  - 0.20 * oi_shift_score
  - 0.15 * volume_expansion_score
- Raw trap score:
  - structural failure
  - wick
  - hold-time failure
  - volume continuation failure
  - volatility factor
  - absorption score
- Warm-up mode downweights wick and hold-time influence.
- Fake-breakout proportional boost still applies when:
  - breakout_strength > 0.7
  - rejection_wick_score > 0.7
  - time_above_level_ratio < 0.3

Trap Classification
backend/app/engines/trap_engine.py
- trap_level thresholds:
  - High: trap_raw > 0.65
  - Moderate: trap_raw > 0.45
  - Low otherwise
- trap_type is now score-gated:
  - aggressive types only assign when trap_raw > 0.45
  - low-risk states no longer emit contradictory labels like Low + Liquidity Sweep

Trap Retail Wrapper
backend/app/engines/trap_engine.py
- Practical trigger context:
  - breakout trigger present
  - weak ATM OI
  - weak volume
  - not in opening 5-minute suppression window
- trap_raw is smoothed across cycles:
  - 0.7 * previous trap_raw
  - 0.3 * current trap_raw
- displayed trap_risk now uses multiplier scaling, not blended floor inflation:
  - is_trap -> 1.25x
  - partial weakness -> 1.10x
  - otherwise 1.0x
- This replaces the earlier blended base formula that artificially pushed low/mid trap toward 50+.

Trap Confidence / Regime Handling
backend/app/services/background_updater.py
- Confidence reduction now applies only to trend-family regimes:
  - Trend Day
  - Breakdown Day
- Range Day skips confidence reduction entirely.
- Trap Day currently also skips confidence reduction by design.
- Validation implication:
  - high-confidence range sessions should not automatically show lower trap.

Trap Range Cap
backend/app/services/background_updater.py
- Quiet range sessions apply a soft trap cap before readiness is computed.
- Condition:
  - committed_regime == Range Day
  - material_breach_confirmed == false
- Effect:
  - trap_probability capped at 72
- Ordering matters:
  - cap is applied before readiness / readiness_active logic

Absorption / Trap Interaction
backend/app/services/background_updater.py
- Absorption is still part of core trap_raw via absorption_score.
- If absorption wins the resolver and action is already forced to WAIT:
  - readiness now skips trap deduction
- Purpose:
  - avoid double penalizing the same absorption signal through both resolver and readiness deduction

Expiry / Session Phase Trap Adjustment
backend/app/engines/expiry_mode_engine.py
- Expiry trap adjustment still exists.
- Current combined trap multiplier:
  - expiry multiplier * phase multiplier
  - capped at 1.5x total
- This prevents expiry-day phase stacking from overshooting intent.
- Current phase references include:
  - Compression Phase
  - Position Build Phase
  - Transition
  - Power Hour

Trade Readiness
backend/app/services/background_updater.py
- Readiness inputs:
  - clarity
  - alignment magnitude
  - execution risk
  - breakout probability
  - trap deduction
- Trap deduction behavior:
  - no deduction below 55
  - above 55 deducts 0.25 per point
  - max deduction = 10
- Deduction is skipped when:
  - breakout_suppressed
  - breakout_candidate
  - absorption already forced WAIT
- Readiness hysteresis:
  - activate at >= 57
  - deactivate below < 53

LONG BIAS Promotion Guard
backend/app/services/background_updater.py
- Validation target:
  - if readiness_active = true and trap < 60 but action remains WAIT, the remaining blocker is in the promotion guard, not the trap stack
- Watch for:
  - readiness_active = true
  - trade_readiness > 57
  - action = WAIT
- That pattern indicates a downstream action promotion condition is still blocking.

Material Breach Engine
backend/app/engines/material_breach_engine.py
- Current-level thresholds:
  - max(50, level * 0.002)
- Confirmation paths:
  - bullish_positioning
  - resistance_abandonment
  - bearish_positioning
  - support_abandonment
- Previous-level override now lives inside material_breach_engine.py itself.
- detect_material_breach(...) explicitly accepts:
  - prev_support
  - prev_resistance
- Validation implication:
  - previous-level abandonment logic is owned by one engine instead of split between engine and updater

Breach Debug Logging
backend/app/engines/material_breach_engine.py
- Positive confirmation debug lines now exist:
  - breach confirmed: side=... dist=... type=... via=...
- Unconfirmed debug lines still log:
  - breach distance

- Validation target:
  - large single-cycle moves should either confirm or emit a useful unconfirmed trace

SR Engine Hysteresis
backend/app/engines/sr_engine.py
- Immediate support/resistance selection holds the previous active level unless the new level is meaningfully stronger.
- Current intended hysteresis:
  - roughly 15 percent OI improvement required to flip immediate support/resistance
- Additional upward resistance promotion buffer:
  - CE resistance cannot promote upward unless spot is at least 25 points above the previous resistance
  - downward reverts remain free
- Purpose:
  - stop 23800 <-> 24000 or equivalent support ping-pong
  - stop premature upward resistance jumps such as 23300 -> 23500 while spot is still below the active resistance
  - allow candidate_regime_count to reach 3

Target / Breakout Probability
backend/app/engines/target_engine.py
backend/app/engines/breakout_probability_engine.py
backend/app/engines/expiry_mode_engine.py
- Targets are anchored to live S/R band width, not stale expectedMove distance.
- Core move base:
  - band_width = resistance - support
  - base_move = band_width * (1 + oi_power) * vol_factor
- Target scaling:
  - target_1 = 0.8x base_move
  - target_2 = 1.5x base_move
  - extended = 2.5x base_move where used
- Target distance clamp:
  - max 3x band from the broken level
- Breakout probability includes proximity weighting:
  - closer to resistance boosts upside
  - closer to support boosts downside

backend/app/services/background_updater.py
backend/app/engines/session_phase_engine.py

Regime Hysteresis
backend/app/services/background_updater.py
- Committed regime uses explicit hysteresis state:
  - committed_regime
  - candidate_regime
  - candidate_regime_count
  - last_detected_regime
- Normal structural shift acceptance pattern:
  - N+0 -> candidate count 1
  - N+1 -> count 2
  - N+2 -> count 3
  - N+3 -> committed flips, candidate clears
- Minimum hold is now required before the candidate ladder starts:
  - detected regime must match previous cycle last_detected_regime
  - one-cycle flickers should not increment candidate_regime_count
- Confirmed material breaches bypass the 3-cycle gate:
  - resistance breach -> Trend Day
  - support breach -> Breakdown Day
  - breach + absorption -> Trap Day

Readiness Stability

Decision UX Layer
backend/app/services/background_updater.py
- market_state now exposes additive UX fields:
  - resolved_reason
  - blocking_reason
  - winning_engine
  - decision_confidence
  - support_transition_badge
  - resistance_transition_badge
  - signal_history
- blocking_reason is a single dominant blocker inferred from the final resolved decision path:
  - transition badges
  - absorption conflict
  - no breach confirmation
  - trap high
  - range conflict
  - promotion guard
  - low readiness
- winning_engine is inferred from the same final path and does not change core resolver behavior.
- decision_confidence is a UI score derived from:
  - trade_readiness base
  - trap reduction
  - transition penalty
  - WAIT / blocker penalties
  - small confirmed-breach lift
- signal_history:
  - stored in _state
  - capped at 10 items
  - only appends when action / resolved_reason / blocking_reason changes
  - intended for recent UI timeline, not analytics

SR Reset / Cold-Start Hydration
backend/app/engines/sr_engine.py
backend/app/services/background_updater.py
- SR hysteresis now hydrates previous support/resistance from persisted top-level state on restart and cold start.
- Purpose:
  - prevent 25-point support / resistance buffers from being bypassed on the first post-restart OI read
- Validation target:
  - no downward support move should occur while spot is still above old support - 25
  - no upward resistance move should occur while spot is still below old resistance + 25

Daily context fetch policy (incremental)
- If no saved file exists:
  - bootstrap with rolling lookback (default 90 days)
- If file exists:
  - read existing rows
  - find latest saved trading date
  - fetch from latest+1 day to today
  - merge, deduplicate, sort
- Purpose:
  - avoid downloading full 3-month history every day
  - keep payload fresh with minimal network load

Do-not-break rule
- Daily context is read-only higher-timeframe context.
- It must not directly drive intraday SPC breach/transition logic.
