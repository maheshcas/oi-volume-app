OptionLens Frontend Validation Logic Overview

Maintenance rule
- Update this file whenever frontend rendering, field mapping, symbol routing, responsive behavior, or UI interpretation changes.

Current Frontend Runtime State
- Desktop dashboard renders at `md` and above.
- Mobile dashboard renders below `md`.
- Both dashboards consume the same backend summary contract.
- Current frontend build supports:
  - `NIFTY`
  - `BANKNIFTY`
  - `FINNIFTY`
  - `SENSEX`

App Shell / Symbol State
frontend/src/App.tsx
- Symbol registry includes:
  - `NIFTY`
  - `BANKNIFTY`
  - `FINNIFTY`
  - `SENSEX`
- Index-name mapping includes:
  - `BSE SENSEX`
- Selected symbol is persisted in localStorage under:
  - `optionlens:selected-symbol`
- Desktop uses a pill-toggle selector instead of a native `<select>`.
- Mobile uses the same symbol list and the same persisted change handler.
- `instrument_type` is initialized as `"Indices"` and sent as a query parameter.
  - The backend validates this as uppercase `"INDICES"` (allowed).
  - The frontend never reads `instrument_type` back from API responses; it is outbound-only.
  - No frontend changes are needed when the backend normalizes `instrument_type` to uppercase.
- Validation targets:
  - selecting `SENSEX` survives refresh
  - symbol changes continue to drive the existing summary endpoint with `?symbol=...`
  - switching symbols does not require component-specific data-shape changes

SPC label correctness
frontend/src/components/StructuralPriceContextCard.tsx
- SPC uses unified label-state resolution (`resolveSPCLabelState`) for:
  - center spot text
  - breach / proximity banner
- Both center text and breach banner are driven by the same resolved state, so they
  always agree.
- Label states: `BELOW_SUPPORT`, `ABOVE_RESISTANCE`, `NEAR_SUPPORT`, `NEAR_RESISTANCE`,
  `LOWER_BAND`, `UPPER_BAND`, `MID_BAND`
- Validation targets:
  - if `spot < support`, center text must say below-support context, not near-support
  - if `spot > resistance`, center text must say above-resistance context, not inside-band
  - breach banner and center text must agree

SPC band / orb behavior
frontend/src/components/StructureBand.tsx
- Active band remains the visual source of truth for structural context.
- State resolved via `resolveSPCState` into one of 6 states; orb theme is derived from state.
- Wide-spread and tight-spread range bounds are handled separately.
- Tight breach states now get extra breached-side breathing room so the orb does not pin
  to the far edge when spot is only slightly outside S/R.
- Extensions (`showLeftExtension` / `showRightExtension`) only appear on genuine
  breakout/breakdown attempts or confirmed expansion; they are not shown on minor proximity.
- Validation targets:
  - spot slightly above R should render as a modest breakout-attempt extension, not an orb
    clipped at the far edge
  - spot slightly below S should behave symmetrically on the left side

Mobile structural range
frontend/src/components/mobile/StructuralRangeTrackMobile.tsx
- Position context uses signed distance:
  - `distToSupport < 0` → below support → renders breach wording (`"X pts below support"`)
  - `distToResistance < 0` → above resistance → renders breach wording (`"X pts above R"`)
- Near-edge wording is only used when distance is positive (spot is inside the band).
- Validation target:
  - broken states must render as breach context, not near-edge context

Frontend / Backend Contract Areas

Summary endpoint usage
frontend/src/App.tsx
- Frontend uses the existing summary contract and changes only the `symbol` query parameter.
- No card-specific symbol branching is required.
- Validation target:
  - `SENSEX` renders through the same normalized card stack as NSE symbols

Backend input validation contract
backend/app/routers/option_chain.py
- The backend now rejects invalid query params with HTTP 400 before cache lookup.
- Allowed symbols: `NIFTY`, `BANKNIFTY`, `FINNIFTY`, `SENSEX` (plus any in `OPTIONLENS_SYMBOLS`).
- Allowed instrument_type values: `INDICES`, `FUTURES`, `EQUITIES` (case-insensitive input).
  - Frontend sends `instrument_type=Indices`; this is accepted and normalized to `INDICES`.
- Expiry format validated as `^[A-Za-z0-9\-]+$`.
- Validation implication: frontend must not send arbitrary strings in these params.
  Current frontend values (`Indices`, valid symbol names, NSE expiry format) all pass.

Previous-level display
frontend/src/components/StructuralPriceContextCard.tsx
